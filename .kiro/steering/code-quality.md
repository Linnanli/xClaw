# 代码质量规范：禁止补丁式代码

## 什么是补丁式代码

补丁式代码（Patch Code）是指在已有实现上不断追加逻辑，而不是重新设计结构。典型特征：

- 在函数末尾追加 `if special_case { ... }`
- 给函数加新参数只为处理一个边缘情况
- 复制粘贴已有逻辑并微调
- 用全局 flag 控制某段代码是否执行
- 注释掉旧代码而不是删除

## 为什么危险

补丁式代码会导致：

1. **逻辑碎片化** — 同一个功能的逻辑散落在多处，读代码时无法建立完整心智模型
2. **测试盲区扩大** — 每个补丁都引入新的执行路径，失败路径测试很容易遗漏
3. **安全风险** — 本项目有 DLP、权限、审计等安全模块，补丁式修改极易破坏 fail-safe 设计（参考 AGENTS.md 中的历史教训）
4. **编译警告累积** — 未使用的参数、死代码会触发 Rust 编译警告，违反 0 警告要求
5. **重构成本指数级增长** — 补丁叠补丁后，任何改动都可能引发连锁反应

## AI 的行为准则

### 写代码前必须做的判断

拿到需求后，先问自己：

1. 现有函数/模块的职责是否还清晰？新需求是否超出了它的职责范围？
2. 是否有 2 处以上相似逻辑可以统一？
3. 最简单的实现是什么？能不能不加新参数、不加新分支就解决？
4. **这个功能有没有成熟的库或平台 API 可以直接用？** 如果有，优先用，不要自己实现。

### 优先使用成熟方案，禁止重复造轮子

**这是与"禁止补丁式代码"同等重要的原则。** 自己从零实现已有成熟方案的功能，本质上也是一种技术债——维护成本高、边界情况多、容易出 bug。

#### 判断流程

遇到一个需求，先按以下顺序检查：

1. **项目内已有实现？** 先搜索 `Cargo.toml`、`package.json`、现有代码，确认是否已有可复用的模块或依赖
2. **框架/平台原生支持？** Tauri、React、Axum 等框架本身是否提供了这个能力（如 Tauri 的插件系统、Axum 的中间件）
3. **成熟社区库？** crates.io / npm 上是否有被广泛使用的库（下载量高、维护活跃、有测试）
4. **以上都没有，才自己实现**

#### 典型反例（本项目真实发生过的教训）

| 需求 | 错误做法 | 正确做法 |
|------|---------|---------|
| Tauri 应用导出文件 | 用 `blob URL` / `data URI` + `a.click()` 自己模拟下载 | 直接用 `@tauri-apps/plugin-dialog` + `@tauri-apps/plugin-fs` |
| 日志系统 | 自己实现环形缓冲区和广播 | 复用项目已有的 `LogBroadcaster`（`ironclaw::channels::web::log_layer`） |
| HTTP 请求 | 手写 TCP 连接 | 用 `reqwest`（项目已有） |

#### 使用外部库的标准

引入新依赖前确认：
- 周下载量 > 10万（npm）或 > 1万（crates.io），或是框架官方插件
- 最近 6 个月有维护（有 commit 或 release）
- 有完整文档和测试
- 许可证与项目兼容（MIT / Apache-2.0 优先）

引入后：
- 先搜索项目中该库的现有用法，参考已有代码而非外部文档
- 检查版本与项目其他依赖的兼容性

### 触发重构的信号

遇到以下情况，必须停下来重构，而不是继续堆叠：

| 信号 | 正确做法 |
|------|---------|
| 函数超过 50 行 | 拆分为多个单一职责函数（Rust 的 match、错误处理链、async 天然占行数，30 行不现实） |
| 嵌套超过 3 层 | 提前返回（early return）或提取子函数 |
| 相似逻辑出现 3 次 | 提取为公共函数或 trait（2 次时可能是巧合，3 次才是模式） |
| 新增参数只服务一个 case | 重新设计函数签名或拆分函数 |
| 需要注释解释"为什么这里要特判" | 这是设计问题，用结构表达意图 |
| 自己实现了一个"轮子" | 检查是否有成熟库，有则替换 |

### 具体操作步骤

**情况 A：新增功能**
1. 先读懂现有相关代码的完整结构
2. 检查是否有成熟库或平台 API 可以直接用（见上方判断流程）
3. 判断新功能是扩展现有抽象，还是需要新抽象
4. 如果是扩展：修改现有结构使其自然容纳新功能
5. 如果是新抽象：创建新模块/函数，不污染现有代码
6. 删除所有因重构变得多余的旧代码

**情况 B：修复 Bug**
1. 找到根本原因，不要只修复症状
2. 如果 bug 是因为设计问题导致的，修复设计而不是加防御性 if
3. 如果 bug 是因为自己实现了本该用成熟库的功能，考虑替换
4. 最小 bug 修复可以例外，但必须留下 TODO 注释标记技术债

**情况 C：发现现有代码已经是补丁式**
1. 标记技术债（TODO 注释），小范围重构与新需求直接相关的代码
2. 不要试图一次性重构整个模块，大范围重构容易引入回归
3. 重构和新功能分两次提交，保持 diff 清晰

## 本项目特别注意

- Rust 的所有权系统会放大补丁式代码的复杂度，不要用 `.clone()` 掩盖所有权设计问题；生产代码避免 `unwrap()`，用 `?` 或 `expect("reason")` 替代
- 安全模块（DLP、权限检查）的任何补丁都必须同步更新失败路径测试
- 新增迁移文件后必须同步更新 `integration_smoke_tests.rs`，不能只加迁移不加验证
- Tauri 插件（`tauri-plugin-*`）是平台官方方案，涉及文件系统、对话框、通知等能力时**必须优先使用插件**，不要用 Web API 模拟
