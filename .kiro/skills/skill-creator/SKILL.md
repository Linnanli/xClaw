# Skill Creator

> 本 skill 基于 Anthropic 官方 skill-creator 插件转换，适配 Kiro 环境。
> 原版依赖 Claude Code 的 subagents、`claude -p` CLI、浏览器 eval viewer 等能力。
> Kiro 版将这些能力替换为对话内直接执行的等效流程。

---

## 核心循环

创建 skill 的过程是一个迭代循环，不是一次性交付：

1. 搞清楚 skill 要做什么，大致怎么做
2. 写一份草稿s
3. 设计 2-3 个测试用例，用 skill 执行它们
4. 帮用户评估结果（定性 + 定量）
5. 根据反馈改写 skill
6. 重复，直到满意
7. 扩大测试集，更大规模验证

你的工作是判断用户在这个流程的哪个阶段，然后帮他们推进。也许他们说"我想做一个 X 的 skill"，你就从头开始。也许他们已经有草稿了，你就直接进入评估/迭代阶段。

当然，要灵活。如果用户说"不需要跑一堆评估，直接和我聊就行"，那就按他们的节奏来。

---

## 与用户沟通

Skill creator 的用户技术水平差异很大。注意上下文线索来调整沟通方式：

- "评估"和"基准测试"这类词可以用，但如果不确定用户是否理解，简短解释一下
- "JSON"和"断言"这类词，除非用户明显懂技术，否则先解释再用
- 简短定义比假设用户都懂要好

## 创建 Skill

### 捕获意图

先理解用户的意图。当前对话可能已经包含了用户想要固化的工作流（比如他们说"把这个变成 skill"）。如果是这样，先从对话历史中提取答案——用了哪些工具、步骤顺序、用户做了哪些纠正、观察到的输入输出格式。用户可能需要补充细节，但在继续之前要确认。

1. 这个 skill 要让 AI 做什么？
2. 什么时候应该触发？（什么用户短语/上下文）
3. 期望的输出格式是什么？
4. 是否需要设置测试用例来验证？有客观可验证输出的 skill（文件转换、数据提取、代码生成、固定工作流步骤）适合测试用例。主观输出的 skill（写作风格、艺术）通常不需要。根据 skill 类型建议合适的默认值，但让用户决定。

### 访谈和调研

主动问清楚边界情况、输入输出格式、示例文件、成功标准和依赖。在写测试用例之前先把这些搞定。

检查项目里是否已有类似 skill（`.kiro/skills/`），避免重复。

### 写 Skill 文件

基于用户访谈，填充以下组件：

**触发描述**（文件开头）— 说明什么时候触发、做什么。这是主要的触发机制——既包含 skill 做什么，也包含什么时候用。所有"什么时候用"的信息放在这里，不放在正文里。

注意：AI 目前倾向于"不够主动"地使用 skill——在应该用的时候不用。为了对抗这个问题，触发描述要稍微"主动"一点。比如，不要写"如何构建一个简单的数据仪表盘"，而是写"如何构建一个简单的数据仪表盘。当用户提到仪表盘、数据可视化、内部指标、或想展示任何数据时，都应该使用这个 skill，即使他们没有明确说'仪表盘'。"

**正文** — skill 的核心指令。

### Skill 写作指南

#### Skill 的结构

```
.kiro/skills/skill-name/
├── skill-name.md          # 必须，skill 主体
└── references/             # 可选，按需加载的详细文档
```

#### 渐进式加载

Skill 使用三层加载系统：
1. 触发描述（文件开头约 100 词）— 始终在上下文中
2. Skill 正文（理想情况下 <500 行）— skill 触发时加载
3. 引用资源（references/ 目录）— 按需加载，不限大小

关键模式：
- Skill 正文控制在 500 行以内；如果接近这个限制，增加一层层级，并在正文中清晰指向 references/ 中的后续内容
- 从正文中清晰引用 reference 文件，说明什么时候读它们

**领域组织**：当 skill 支持多个领域/框架时，按变体组织：
```
cloud-deploy/
├── skill-name.md        # 工作流 + 选择逻辑
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
AI 只读取相关的 reference 文件。

#### 写作模式

用祈使句写指令。

**定义输出格式**：
```markdown
## 报告结构
始终使用以下模板：
# [标题]
## 执行摘要
## 关键发现
## 建议
```

**示例模式**：
```markdown
## 提交信息格式
**示例 1：**
输入：添加了 JWT 用户认证
输出：feat(auth): implement JWT-based authentication
```

### 写作风格

尽量向模型解释事情为什么重要，而不是堆砌沉重的 MUST。运用 theory of mind，让 skill 通用而不是过度针对特定例子。先写一份草稿，然后用全新的眼光审视并改进。

如果发现自己在写全大写的 ALWAYS 或 NEVER，或者用超级僵硬的结构，这是一个黄色信号——如果可能的话，重新组织并解释原因，让模型理解你要求的事情为什么重要。这是一种更人性化、更强大、更有效的方法。

## 测试用例

写完 skill 草稿后，设计 2-3 个真实的测试用例——真实用户实际会说的话。和用户分享："这是我想试的几个测试用例，看起来对吗？还是你想加更多？"然后执行它们。

将测试用例保存为结构化格式：

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "用户的任务提示",
      "expected_output": "期望结果的描述",
      "expectations": [
        "输出包含 X",
        "使用了 Y 格式"
      ]
    }
  ]
}
```

## 运行和评估测试用例

这是一个连续的流程——不要中途停下来。

将结果组织在 `skill-name-workspace/` 目录中，按迭代（`iteration-1/`、`iteration-2/`）和测试用例（`eval-0/`、`eval-1/`）分目录。不要预先创建所有目录——用到时再创建。

### 步骤 1：执行测试

> **Kiro 适配说明**：原版使用 subagents 并行执行"有 skill"和"无 skill"两组测试。
> 在 Kiro 中，改为串行执行：先读取 skill 内容，然后按照 skill 指令完成每个测试用例。
> 如果是新建 skill，跳过 baseline（无 skill）对比。
> 如果是改进已有 skill，先保存旧版本快照，再用新版本执行，然后对比。

对每个测试用例：
1. 读取 skill 的内容
2. 按照 skill 指令完成测试任务
3. 将输出保存到对应的 eval 目录

### 步骤 2：设计断言

在执行测试的同时，为每个测试用例设计量化断言。好的断言是客观可验证的，并且有描述性的名称——让人一眼就能理解每个断言检查什么。

主观 skill（写作风格、设计质量）更适合定性评估——不要强行给需要人类判断的东西加断言。

### 步骤 3：评分

对每个测试运行的输出进行评分。评估每个断言是否通过：

**通过条件**：
- 输出中有明确证据表明断言为真
- 证据反映的是真正的任务完成，不只是表面合规
- 可以引用具体的文本或描述

**失败条件**：
- 没有找到证据
- 证据与断言矛盾
- 证据是表面的——断言技术上满足了，但底层任务结果是错误或不完整的

**不确定时**：举证责任在断言一方——不确定就判失败。

评分时还要做两件额外的事：

1. **提取和验证隐含声明**——除了预定义的断言，从输出中提取隐含声明并验证。比如"表单有 12 个字段"是事实声明，"使用了 pypdf 填充表单"是过程声明。这能捕获预定义断言可能遗漏的问题。

2. **批评断言本身**——一个通过了弱断言的结果比没用还糟糕，因为它制造了虚假信心。如果发现某个断言即使输出明显错误也会通过（比如只检查文件名存在但不检查内容），或者某个重要结果没有任何断言覆盖，指出来。

### 步骤 4：汇总和展示

> **Kiro 适配说明**：原版使用 `generate_review.py` 生成浏览器 HTML 界面。
> 在 Kiro 中，直接在对话中展示结果。

对每个测试用例，向用户展示：
- **提示**：给出的任务
- **输出**：skill 产生的结果
- **评分**：每个断言的通过/失败及证据
- **统计**：通过率汇总

如果是迭代 2+，还要展示上一轮的输出和反馈，方便对比。

然后告诉用户："结果在上面。你可以逐个看每个测试用例，告诉我哪些地方需要改进。"

### 步骤 5：收集反馈

用户的反馈可能是：
- 具体的改进意见（"图表缺少坐标轴标签"）
- 没有反馈（表示满意）
- 整体评价（"完美，就是这样"）

没有反馈的测试用例意味着用户觉得没问题。把改进精力集中在用户有具体意见的测试用例上。

## 改进 Skill

这是循环的核心。你已经运行了测试用例，用户已经审查了结果，现在你需要根据反馈让 skill 变得更好。

### 如何思考改进

1. **从反馈中泛化。** 这里的大局是：我们在创建可能被使用百万次的 skill，跨越许多不同的提示。你和用户在这里只是在几个例子上反复迭代，因为这样更快。用户对这些例子了如指掌，能快速评估新输出。但如果你们共同开发的 skill 只对这些例子有效，它就是无用的。与其加入琐碎的过拟合修改或压迫性的 MUST 约束，如果有某个顽固问题，不如尝试换个角度，用不同的隐喻，或推荐不同的工作模式。尝试的成本相对较低，也许你会找到很棒的方案。

2. **保持精简。** 删掉没有贡献的内容。如果从测试执行过程中看到 skill 让模型浪费大量时间做无效的事情，试着去掉导致这种行为的 skill 部分，看看会怎样。

3. **解释原因。** 尽力解释你要求模型做的每件事背后的"为什么"。今天的 LLM 很聪明。它们有良好的 theory of mind，在好的框架下能超越机械指令，真正把事情做好。即使用户的反馈简短或沮丧，也要真正理解任务、理解用户为什么这样写、他们实际写了什么，然后把这种理解传递到指令中。如果发现自己在写全大写的 ALWAYS 或 NEVER，或使用超级僵硬的结构，这是一个黄色信号——如果可能的话，重新组织并解释原因，让模型理解为什么你要求的事情很重要。这是更人性化、更强大、更有效的方法。

4. **寻找跨测试用例的重复工作。** 阅读测试运行的过程，注意是否所有测试用例都独立写了类似的辅助脚本或采取了相同的多步骤方法。如果所有 3 个测试用例都导致写了一个 `create_docx.py` 或 `build_chart.py`，这是一个强信号——skill 应该把那个脚本打包进去。写一次，放到 `scripts/`，告诉 skill 使用它。这能让未来每次调用都不用重新发明轮子。

### 迭代循环

改进 skill 后：

1. 应用改进
2. 重新运行所有测试用例到新的 `iteration-<N+1>/` 目录
3. 向用户展示结果，包含与上一轮的对比
4. 等待用户审查并告诉你完成了
5. 读取新反馈，再次改进，重复

持续直到：
- 用户说满意了
- 所有反馈都是空的（一切看起来都好）
- 没有在取得有意义的进展

## 高级：盲评对比

> **Kiro 适配说明**：原版使用独立的 comparator subagent 做盲评。
> 在 Kiro 中，你自己扮演盲评角色。

当需要更严格地对比两个版本的 skill 时（比如用户问"新版本真的更好吗？"），可以做盲评对比：

1. 准备两个版本的输出，标记为 A 和 B（不要在心里关联哪个是新版哪个是旧版）
2. 生成评估量规：
   - 内容维度（正确性、完整性、准确性）— 每项 1-5 分
   - 结构维度（组织性、格式、可用性）— 每项 1-5 分
3. 对每个输出逐项评分
4. 检查断言通过率（如果有）
5. 确定赢家，给出具体理由

要果断——平局应该很少见。一个输出通常更好，即使只是略微更好。

### 分析为什么赢家赢了

确定赢家后，分析原因：

- 赢家的 skill 有什么更好的指令导致了更好的行为？
- 输家的 skill 有什么模糊的指令导致了次优选择？
- 有没有缺失的工具/脚本迫使了变通方案？
- 边界情况覆盖有什么差距？

生成可操作的改进建议，按影响优先级排序：
- **高**：可能改变对比结果的改动
- **中**：会提升质量但可能不改变胜负
- **低**：锦上添花

## 触发描述优化

Skill 文件开头的触发描述是决定 AI 是否加载 skill 的主要机制。创建或改进 skill 后，提议优化触发描述以提高触发准确率。

### 步骤 1：生成触发评估查询

创建 20 个评估查询——混合"应该触发"和"不应该触发"的。

```json
[
  {"query": "用户提示", "should_trigger": true},
  {"query": "另一个提示", "should_trigger": false}
]
```

查询必须是真实的，是用户实际会输入的内容。不是抽象请求，而是具体的、有细节的请求——文件路径、个人上下文、列名和值、公司名、URL。一些可能是小写的，包含缩写或错别字或口语。使用不同长度的混合，重点放在边界情况而不是明显的情况。

**应该触发的查询**（8-10 个）：覆盖同一意图的不同表述——有些正式，有些随意。包含用户没有明确提到 skill 或文件类型但明显需要它的情况。

**不应该触发的查询**（8-10 个）：最有价值的是"差一点"的查询——与 skill 共享关键词或概念但实际需要不同东西的查询。不要让不应该触发的查询明显无关。"写一个斐波那契函数"作为 PDF skill 的反面测试太简单了——它什么都测不出来。

### 步骤 2：与用户确认

把评估集展示给用户审查。用户可以编辑查询、切换应该/不应该触发、添加/删除条目。

### 步骤 3：手动优化

> **Kiro 适配说明**：原版使用 `run_loop.py` 脚本自动化优化，通过 `claude -p` CLI 多次运行。
> 在 Kiro 中，改为手动分析和优化。

分析当前触发描述在评估集上的表现：
1. 对每个查询，判断当前描述是否会导致正确的触发/不触发决策
2. 找出失败的模式——是描述太宽泛（误触发）还是太狭窄（漏触发）？
3. 改写描述，解决发现的问题
4. 重新评估，重复直到满意

### 触发机制原理

理解触发机制有助于设计更好的评估查询。Skill 的触发描述出现在 AI 的可用 skill 列表中，AI 根据描述决定是否加载 skill。重要的是：AI 只在自己不能轻松处理的任务上才会加载 skill——简单的一步查询如"读这个 PDF"可能不会触发 skill，即使描述完美匹配，因为 AI 可以用基本工具直接处理。复杂的、多步骤的、专业化的查询在描述匹配时会可靠地触发 skill。

这意味着评估查询应该足够实质性，让 AI 确实会从加载 skill 中受益。

### 步骤 4：应用结果

用优化后的描述更新 skill 文件开头。向用户展示前后对比。

## Kiro Skill 安装

创建好的 skill 放到：
```
.kiro/skills/<skill-name>/<skill-name>.md
```

Kiro 会自动识别 `.kiro/skills/` 下的所有 skill。

如果 skill 有引用资源：
```
.kiro/skills/<skill-name>/
├── <skill-name>.md
└── references/
    ├── detail-guide.md
    └── examples.md
```

## 评估 JSON Schema 参考

### evals.json

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "用户的任务提示",
      "expected_output": "期望结果的描述",
      "files": [],
      "expectations": [
        "输出包含 X",
        "使用了 Y 格式"
      ]
    }
  ]

```

### grading.json

```json
{
  "expectations": [
    {
      "text": "输出包含姓名 'John Smith'",
      "passed": true,
      "evidence": "在步骤 3 中找到：'提取的姓名：John Smith, Sarah Johnson'"
    }
  ],
  "summary": {
    "passed": 2,
    "failed": 1,
    "total": 3,
    "pass_rate": 0.67
  },
  "claims": [
    {
      "claim": "表单有 12 个可填字段",
      "type": "factual",
      "verified": true,
      "evidence": "在 field_info.json 中计数了 12 个字段"
    }
  ],
  "eval_feedback": {
    "suggestions": [
      {
        "assertion": "输出包含姓名 'John Smith'",
        "reason": "一个虚构的文档如果提到了这个名字也会通过——考虑检查它是否作为主要联系人出现"
      }
    ],
    "overall": "断言检查了存在性但没有检查正确性。"
  }
}
```

## 核心循环总结

再强调一次核心循环：

1. 搞清楚 skill 是关于什么的
2. 起草或编辑 skill
3. 用测试用例执行 skill
4. 与用户一起评估输出：
   - 展示结果让用户审查
   - 运行量化评估
5. 重复直到你和用户都满意
6. 优化触发描述
