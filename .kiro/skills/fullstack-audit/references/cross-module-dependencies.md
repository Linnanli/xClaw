# IronClaw 跨模块依赖关系图

本文件记录模块之间的数据流依赖。做业务语义分析时，用这张图快速定位当前模块的上下游。

## 依赖关系总览

```
部门管理(4) ──→ Token 配额检查(18) ──→ 客户端 AI 请求拦截
           ──→ 模型白名单(10) ──→ 客户端可用模型列表
           ──→ 技能/插件白名单(14) ──→ 客户端可用技能列表
           ──→ 知识库访问权限(17) ──→ 客户端知识库检索
           ──→ 客户端配置差异化(9) ──→ 客户端运行参数

DLP 规则(5) ──→ 客户端消息扫描 ──→ 拦截/放行决策
           ──→ 告警触发(15) ──→ 通知发送
           ──→ 对话审计标记(16)
           ──→ 数据分级关联(19)

敏感操作(6) ──→ 客户端操作拦截 ──→ 审批流(21)
            ──→ 审计记录(11)

            ──→ 调用统计 ──→ 告警触发(15)
            ──→ Token 计费(18)

策略版本(7) ──→ 策略签名 ──→ 客户端策略推送(8)
           ──→ 策略变更记录 ──→ 审计(11)

告警系统(15) ←── DLP 拦截事件(5)
            ←── 配额超限事件(18)
            ←── 模型异常事件(10)
            ←── 异常登录事件(1)
            ──→ 通知渠道发送
            ──→ 仪表盘告警徽标(2)

审计日志(11) ←── 所有 CRUD 操作
            ←── 登录事件(1)
            ←── 审批流程(21)
            ←── 配置变更(13)
```

## 常见断裂模式

### 关键架构决策（影响所有分析）

IronClaw 的 AI 对话采用客户端直连模式：
- 后台配置模型信息（包括 API Key）→ 通过 `/api/client-models` 下发给客户端 → 客户端拿 Key 直接调 LLM API
- 这意味着 API Key 必须下发到客户端，费用计算也发生在客户端侧（客户端上报 usage 数据给后端计费）
- 安全审视时要注意：Key 在传输和客户端内存中的保护

以下是这个项目中反复出现的断裂模式，分析时优先检查：

1. 管理后台配了 X，但客户端没有拉取/执行 X 的逻辑
2. 某个事件应该触发告警，但没有代码往 Alert_Service 发事件
3. 某个操作应该写审计日志，但 handler 里没调用 write_audit_log
4. 某个数据有配置 API，但没有对应的查询 API 给消费方用
5. 删除操作只检查了直接关联，没清理间接关联的数据（孤儿数据）
6. 敏感数据在某一层做了脱敏，但在另一层（日志、错误响应）泄露了
