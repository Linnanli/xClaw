## 为什么分成两个用户交互层？

### 1. **使用场景不同**

**Tauri 桌面客户端**:
- 本地用户使用
- 需要离线工作
- 需要本地文件访问
- 需要系统集成（通知、快捷键等）
- 需要本地数据加密存储
- 单用户本地应用

**Web 前端**:
- 远程用户使用
- 需要网络连接
- 浏览器访问
- 跨平台（Windows/Mac/Linux/Mobile）
- 云端数据存储
- 多用户实时协作

### 2. **实际应用场景**

**场景 A：企业员工（办公室）**
```
员工 A (办公室，网络稳定)
  ↓
Web 前端 (浏览器)
  ↓
src/channels/web/ API
  ↓
PostgreSQL (云端)
```

**场景 B：远程工作者（网络不稳定）**
```
员工 B (家里，网络不稳定)
  ↓
Tauri 桌面客户端 (离线模式)
  ↓
libSQL (本地加密)
  ↓
网络恢复后同步到 PostgreSQL
```

**场景 C：移动用户**
```
用户 C (手机)
  ↓
Web 前端 (移动浏览器)
  ↓
src/channels/web/ API
  ↓
PostgreSQL (云端)
```

**场景 D：同一用户多设备**
```
用户 D (办公室)
  ↓
Web 前端 (浏览器)
  ↓
PostgreSQL (云端)

用户 D (家里)
  ↓
Tauri 桌面客户端 (离线)
  ↓
libSQL (本地) → 同步到 PostgreSQL
```

### 3. **架构优势**

**分离的好处**:
- ✅ 各自优化（Tauri 优化本地体验，Web 优化云端体验）
- ✅ 独立部署（可以分别更新）
- ✅ 独立扩展（Tauri 用户不影响 Web 用户）
- ✅ 代码复用（共享后端 API）

**统一的好处**:
- ✅ 共享同一个后端 API (`src/channels/web/`)
- ✅ 共享同一个认证系统 (`src/auth/`)
- ✅ 共享同一个数据库 (PostgreSQL)
- ✅ 用户数据同步

### 4. **数据同步**

```
Tauri 客户端 (离线)
  ↓
本地 libSQL
  ↓
[网络恢复]
  ↓
同步到 PostgreSQL
  ↓
Web 前端 (实时更新)
```

## 总结

**分成两个用户交互层的原因**:

1. **使用场景不同** - 本地 vs 远程
2. **功能需求不同** - 离线 vs 实时协作
3. **用户群体不同** - 桌面用户 vs 移动/浏览器用户
4. **技术优化不同** - 本地优化 vs 云端优化
5. **部署灵活性** - 可以独立扩展

**但它们共享**:
- 同一个后端 API
- 同一个认证系统
- 同一个数据库
- 同一个业务逻辑

这样的设计既保证了灵活性，又保证了一致性。
