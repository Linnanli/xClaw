# Copilot CLI 多 Agent 编排与观测设计

## 1. 背景

当前 x-claw 需要并行推进两条高耦合功能线：

1. 告警中心
2. 审批工单

单个 agent 串行开发的主要问题是吞吐不足；多个 agent 并行开发的主要问题是共享文件冲突、子模块指针冲突、迁移冲突、以及测试与收口失控。

本设计文档定义一套正式的 Copilot CLI 多 agent 编排方案，用于在安装并可用 Copilot CLI 后，为 x-claw 提供可执行、可监控、可收口的并行开发机制。

## 2. 设计目标

### 2.1 目标

1. 让主 agent 能按轮次调度多个子 agent 并行工作。
2. 让每个子 agent 在独立 worktree 中开发，减少上下文和工作区干扰。
3. 让每个子 agent 在进入编码前先执行一次 fullstack-audit，先确认端到端链路和断裂点。
3. 让主 agent 能监控子 agent 的阶段、日志、改动面和阻塞项。
4. 让共享高冲突文件有统一入口，不允许两个子 agent 同时无序改动。
5. 让新增后端、桌面端、migration、Tauri 命令的变更继续遵守仓库既有架构和测试规则。

### 2.2 非目标

1. 不追求完全无人值守的长时间自治开发。
2. 不依赖读取 agent 的完整内部推理链。
3. 不把 Copilot CLI 视为完整工作流平台；缺失部分由仓库内脚本和状态文件补足。
4. 不在本阶段直接引入第四个以上常驻 worker。

## 3. 约束与前提

### 3.1 仓库约束

1. 必须遵守 AGENTS.md 中的复用优先原则。
2. Desktop Client 新能力优先复用主项目 Web Gateway API 或共享 crate。
3. Admin Backend 新模块优先通过 ironclaw crate 或共享 crate 复用主项目能力。
4. 新增 Rust 功能遵循 TDD，且必须执行 cargo build 验证。
5. 新增 migration、Tauri 命令、契约接口时，必须同步补对应测试。

### 3.2 Git 与工作区约束

1. 顶层仓库使用 git worktree 作为并行工作区隔离机制。
2. ironclaw 为子模块，子模块内部改动与顶层子模块指针更新必须分阶段收口。
3. 任一子 agent 不得单独决定顶层 ironclaw 子模块最终指针。

### 3.3 Copilot CLI 前提

本设计默认以下条件已经满足：

1. 本机已安装并认证 Copilot CLI。
2. CLI 支持自定义 agent profile。
3. CLI 支持单次 prompt 执行和机器可读输出。
4. CLI 支持 lifecycle hooks，例如 preToolUse、postToolUse、agentStop。

若其中任一条件不满足，则只能退化为 VS Code 内手动触发模式，不能进入本设计的完整实施阶段。

## 4. 总体方案

### 4.1 架构原则

本方案采用“三层治理”模型：

1. 执行隔离层：一个子 agent 对应一个 worktree。
2. 变更治理层：子 agent 只处理自己边界内的小步改动，禁止提前改共享高冲突区。
3. 集成收口层：由主 agent 决定 foundation 抽取、共享文件改动、测试补齐和最终合并顺序。

### 4.2 运行模式

本方案采用轮次制，不采用无限自治模式。

进入任何编码轮次之前，每个子 agent 必须先执行一次 fullstack-audit。该审查不是可选准备动作，而是编码前置门禁。

每一轮固定为以下顺序：

1. 子 agent 执行或刷新本功能线的 fullstack-audit。
2. 主 agent 读取审查结果、状态与日志。
3. 主 agent 为每个子 agent 下发本轮目标、边界和禁改区。
4. 子 agent 在各自 worktree 内执行本轮任务。
5. 子 agent 输出结构化状态和日志。
6. 主 agent 汇总结果，决定继续、暂停、抽 foundation，或进入测试/收口阶段。

轮次制的核心目的是把不可控的长会话拆成可检查、可中断、可回滚的小步迭代。

### 4.3 编码前置审查门

每个子 agent 的首轮任务固定为 fullstack-audit，且必须覆盖以下内容：

1. 读取 `.kiro/specs/admin-platform-requirements/requirements.md`，定位对应验收标准。
2. 读取 `fullstack-audit` 依赖的参考资料，至少包括 project-map 与 cross-module-dependencies。
3. 按“配置方-消费方”模型识别端到端业务链路和断裂点。
4. 检查设计图、后台 API、后台前端、桌面客户端、数据库迁移、测试覆盖的当前状态。
5. 输出高影响盲区、P0/P1/P2 待办和建议的最小闭环。

未完成上述审查前，子 agent 不得直接进入实现阶段。

## 5. Agent 拓扑

### 5.1 主 agent

主 agent 运行在主仓库，职责如下：

1. 维护全局任务分发与轮次状态。
2. 分配 alert-center 和 approval-workorder 两条功能线的下一轮任务。
3. 监控子 agent 的行为、进度、阻塞、测试结果与共享风险。
4. 决定是否抽取 shared foundation。
5. 决定共享高冲突文件的修改时机与责任归属。
6. 决定最终测试顺序与合并顺序。

主 agent 不直接承担告警中心或审批工单的日常实现，除非用户明确要求接管。

### 5.2 子 agent

初始只启用两个长期 worker：

1. alert-center worker
2. approval-workorder worker

每个 worker 只在自己的 worktree 中执行任务，并对自己的功能线负责。

每个 worker 的首轮职责不是写代码，而是执行 fullstack-audit，并把结果返回给主 agent。审查输出至少包括：

1. 端到端业务流程描述。
2. 配置方-消费方依赖表。
3. 各层实现状态表。
4. 高影响盲区列表。
5. P0/P1/P2 优先级待办。
6. 推荐的最小闭环切入点。

主 agent 只有在读完该审查输出后，才允许向对应 worker 下发编码轮次任务。

### 5.3 两个子 agent 的主任务定义

#### 5.3.1 alert-center worker

alert-center worker 的长期主任务固定为“告警中心全链路落地”，不承担审批工单业务实现。

其主任务包括：

1. 执行 alert-center 对应的 fullstack-audit。
2. 打通告警中心最小闭环：规则 CRUD -> 事件列表 -> 状态更新 -> 仪表盘或侧边栏徽标。
3. 补齐告警中心链路上的失败路径、契约测试、必要的集成验证。
4. 在需要客户端消费时，检查并补齐桌面端或前端消费链路。
5. 将发现的共享抽象冲突、migration 需求、子模块公共能力需求上报给主 agent。

其默认禁止事项包括：

1. 不实现审批工单业务逻辑。
2. 不主动修改共享高冲突区。
3. 不单独决定 foundation 抽取方案。
4. 不单独更新顶层 ironclaw 子模块指针。

其单轮交付物至少包括：

1. 本轮完成项。
2. 当前阻塞项。
3. 触及文件清单。
4. 是否命中共享风险。
5. 下一轮建议。

#### 5.3.2 approval-workorder worker

approval-workorder worker 的长期主任务固定为“审批工单全链路落地”，不承担告警中心业务实现。

其主任务包括：

1. 执行 approval-workorder 对应的 fullstack-audit。
2. 打通审批工单最小闭环：创建工单 -> 审批列表 -> 审批动作 -> 结果回传客户端。
3. 补齐审批链路上的失败路径、契约测试、必要的集成验证。
4. 在需要客户端消费时，检查并补齐桌面端或前端消费链路。
5. 将发现的共享抽象冲突、migration 需求、子模块公共能力需求上报给主 agent。

其默认禁止事项包括：

1. 不实现告警中心业务逻辑。
2. 不主动修改共享高冲突区。
3. 不单独决定 foundation 抽取方案。
4. 不单独更新顶层 ironclaw 子模块指针。

其单轮交付物至少包括：

1. 本轮完成项。
2. 当前阻塞项。
3. 触及文件清单。
4. 是否命中共享风险。
5. 下一轮建议。

#### 5.3.3 首轮 fullstack-audit 标准输出模板

两个子 agent 的首轮审查输出必须使用统一结构，便于主 agent 汇总、比对和后续脚本解析。

必须字段如下：

1. 功能线名称
2. 需求范围
3. 端到端业务流程
4. 配置方-消费方依赖表
5. 各层实现状态表
6. 高影响盲区
7. P0/P1/P2 待办
8. 推荐最小闭环
9. 共享风险判断
10. 建议是否进入编码轮次

建议输出模板如下：

```markdown
## fullstack-audit 结果

### 1. 功能线
- 名称：alert-center | approval-workorder
- 需求范围：[需求编号、模块范围、明确不包含的子范围]

### 2. 端到端业务流程
[用 5-10 行描述从配置方到消费方的完整链路]

### 3. 配置方-消费方依赖表
| 功能点 | 配置方 | 消费方 | 链路状态 | 说明 |
| --- | --- | --- | --- | --- |
| ... | ... | ... | ✅ 完整 / ⚠️ 部分 / ❌ 断裂 | ... |

### 4. 各层实现状态
| 层级 | 状态 | 详情 |
| --- | --- | --- |
| 需求 spec | ✅/⚠️/❌ | ... |
| 设计图 | ✅/⚠️/❌ | ... |
| 后台 API | ✅/⚠️/❌ | ... |
| 后台前端 | ✅/⚠️/❌ | ... |
| 桌面客户端 | ✅/⚠️/❌/N/A | ... |
| 数据库迁移 | ✅/⚠️/❌ | ... |
| 测试覆盖 | ✅/⚠️/❌ | ... |

### 5. 高影响盲区
| 等级 | 问题 | 影响 | 建议 |
| --- | --- | --- | --- |
| 🔴/🟡 | ... | ... | ... |

### 6. 待办列表
1. [P0] ...
2. [P1] ...
3. [P2] ...

### 7. 推荐最小闭环
- 目标链路：...
- 本轮不应触碰的共享区：...
- 完成判据：...

### 8. 共享风险判断
- 是否涉及高冲突区：是/否
- 是否需要 foundation：是/否
- 是否涉及 migration：是/否
- 是否涉及 ironclaw 公共抽象：是/否

### 9. 编码建议
- 建议进入编码轮次：是/否
- 若是：建议首轮编码任务 = ...
- 若否：需要先补的前置事项 = ...
```

主 agent 在消费首轮审查结果时，至少要核对以下事项：

1. 是否明确写出了推荐最小闭环。
2. 是否明确写出了共享风险判断。
3. 是否把 spec、设计图、后端、前端、客户端、迁移、测试七层状态都覆盖到。
4. 是否给出了可以直接转成编码任务的 P0 项。

若任一项缺失，主 agent 应要求对应 worker 先补审查，而不是直接发编码任务。

### 5.4 可选 foundation worker

只有在共享抽象被两条功能线同时触发时，才引入 foundation worker。其职责不是做第三条业务线，而是处理：

1. 共享 backend service 抽取
2. 共享 event/model 抽取
3. 共享 Tauri 注册骨架
4. 共享 migration 方案
5. 子模块内部共享基础能力

默认情况下，不启用 foundation worker，以避免编排复杂度过高。

## 6. Worktree 与分支模型

### 6.1 固定工作区

1. 主控仓库：x-claw
2. 告警线：x-claw.worktrees/alert-center
3. 审批线：x-claw.worktrees/approval-workorder

### 6.2 分支约束

1. 每个 worker 只在自己的功能分支上提交。
2. 顶层仓库分支与 ironclaw 子模块内部功能分支分开管理。
3. 顶层仓库的子模块指针更新只能在共享收口阶段执行。

### 6.3 合并顺序

固定顺序如下：

1. 共享 foundation 分支（若有）
2. ironclaw 子模块内部功能分支
3. 顶层仓库中的 ironclaw 子模块指针更新
4. 顶层业务功能分支

该顺序用于避免顶层仓库过早锁定子模块指针，导致多个 worktree 反复冲突。

## 7. 状态、日志与观测模型

### 7.1 观测目标

主 agent 需要观测的不是子 agent 的完整思维，而是工程上足够决策的行为信号。

必须可观测的维度包括：

1. 子 agent 当前是否在运行。
2. 子 agent 当前处于哪个阶段。
3. 子 agent 最近触及了哪些文件。
4. 子 agent 本轮完成了什么、阻塞了什么。
5. 子 agent 是否触发共享风险。
6. 子 agent 是否通过了本轮最小验证。

### 7.2 状态载体

正式方案不再为每个阶段维护大量手工计划文档，而采用以下三类载体：

1. 一份正式设计文档，定义规则与架构。
2. 每轮运行生成的结构化状态文件，其中首轮必须包含 fullstack-audit 摘要。
3. 每轮运行生成的 hooks 日志与 git 摘要。

### 7.3 建议目录

建议后续实现时新增以下目录与文件：

1. scripts/agents/
2. logs/agents/
3. docs/plans/agent-runs/
4. .github/hooks/copilot-cli-hooks.json

其中：

1. logs/agents 用于存放原始 hook 日志。
2. docs/plans/agent-runs 用于存放每轮状态快照。
3. scripts/agents 用于存放启动、汇总、冲突检查脚本。

### 7.4 Hook 事件

建议至少记录以下事件：

1. preToolUse
2. postToolUse
3. agentStop

每条事件至少包含：

1. 时间戳
2. agent 名称
3. 所属 worktree
4. 工具或命令名称
5. 执行结果摘要
6. 当前轮次编号

### 7.5 主 agent 汇总视图

主 agent 每轮应汇总以下信息：

1. 两个 worker 的状态摘要
2. 两个 worktree 的 git status
3. 两个 worktree 的 git diff --stat
4. 最近一次测试结果摘要
5. 共享风险命中情况

主 agent 的决策不应只依赖子 agent 自报，必须与 git 和测试结果交叉校验。

## 8. 冲突治理

### 8.1 高冲突区

以下路径默认视为共享高冲突区：

1. admin-backend/src/routes.rs
2. admin-backend/src/models.rs
3. admin-backend/tests/integration_smoke_tests.rs
4. desktop-client/src/lib.rs
5. desktop-client/tests/tauri_command_contract_tests.rs
6. admin-backend/migrations/
7. 顶层 ironclaw 子模块指针

### 8.2 默认规则

1. 子 agent 默认不得修改高冲突区。
2. 若本轮任务必须触及高冲突区，需由主 agent 明确授权。
3. 两个子 agent 不得在同一轮内同时修改同一高冲突区。
4. 任何 migration 变更都视为共享风险，不允许静默推进。

### 8.3 Foundation 触发条件

满足任意一条时，应暂停至少一条功能线并转入 foundation 处理：

1. 两条功能线都需要改公共事件模型。
2. 两条功能线都需要改同一套公共 service 或查询抽象。
3. 两条功能线都需要改 Tauri 命令注册骨架。
4. 两条功能线都需要新增或修改 schema。
5. 两条功能线都需要改 ironclaw 中同一层抽象。

## 9. 任务分发原则

### 9.1 任务粒度

主 agent 下发的任务必须足够小，要求：

1. 一轮只解决一条最小链路或一个共享问题。
2. 每轮结束时必须可以形成可验证输出。
3. 不允许用“继续完善”这类模糊目标作为单轮任务。

额外要求：

1. 每条功能线的第一个可执行任务必须是 fullstack-audit，而不是直接编码。
2. 首次编码任务必须明确引用对应审查结论中的 P0 或最小闭环项。

### 9.2 功能线优先级

告警中心优先闭环：

1. 规则 CRUD
2. 事件列表
3. 状态更新
4. 仪表盘或侧边栏徽标

审批工单优先闭环：

1. 创建工单
2. 审批列表
3. 审批动作
4. 结果回传客户端

主 agent 应优先让两条功能线都完成各自最小闭环，再进入共享收口阶段。

## 10. 测试与质量闸门

### 10.1 基本闸门

任何一轮进入“可合并候选”前，至少满足：

1. 涉及的 Rust 工程 cargo build 通过。
2. 对应的单元测试与失败路径测试已补齐或明确标记阻塞。
3. 若新增 API 或命令，契约测试同步更新。
4. 若新增 migration，integration_smoke_tests.rs 同步更新。

### 10.2 组合测试

当某条功能线涉及多角色、多状态、多失败路径或权限组合时，应进入 pairwise 测试设计流程。

规则如下：

1. 先用 pict-test-designer 设计参数、取值和约束。
2. 满足高风险条件时，再用 pairwise-test-generator 与 scripts/pict_generate.py 生成组合。
3. 组合结果必须映射回现有测试族，而不是另起一套平行测试体系。

### 10.3 真环境边界

以下问题不得只靠 mock 验证：

1. SSE 事件格式
2. Tauri 状态注入
3. migration 完整性
4. 安全相关失败路径

## 11. 实施阶段

### 阶段 1：CLI 能力校验

目标：确认 Copilot CLI 在本机可稳定运行。

输出：

1. CLI 安装与认证通过
2. 自定义 agent profile 可识别
3. 单次 prompt 与 JSON 输出可用
4. hook 机制可落日志

### 阶段 2：子 agent 首轮 fullstack-audit

目标：让 alert-center 与 approval-workorder 两个 worker 在各自 worktree 中先完成一次审查，再进入编码。

输出：

1. 每条功能线的端到端业务流程描述
2. 配置方-消费方依赖表
3. 各层实现状态表
4. 高影响盲区清单
5. P0/P1/P2 待办与最小闭环建议

主 agent 在这一阶段的职责是消费两份审查结果，并据此决定首个编码轮次的边界。

### 阶段 3：最小编排骨架

目标：建立主 agent + 两个 worker 的最小可运行闭环。

输出：

1. 启动脚本
2. 日志目录
3. 状态快照目录
4. 轮次汇总脚本

### 阶段 4：冲突防护

目标：在进入真实功能开发前，把高冲突检测和禁改规则固化到脚本层。

输出：

1. 路径级红线检查
2. 同轮冲突检测
3. foundation 触发判断

### 阶段 5：真实功能试运行

目标：在 alert-center 与 approval-workorder 上执行第一轮真实并行开发。

输出：

1. 两条功能线各自的最小闭环
2. 轮次日志与状态可追踪
3. 主 agent 可基于状态和日志作出下一轮决策

### 阶段 6：测试与收口

目标：把编排模式推广到测试设计、共享收口和合并准备。

输出：

1. pairwise 触发规则接入
2. 共享基础分支处理流程
3. 合并顺序与最终验收清单

## 12. 风险与缓解

### 风险 1：CLI 能力不足

表现：CLI 缺少稳定的 JSON 输出、hook 或自定义 agent 支持。

缓解：

1. 降级为 VS Code agent + 外层 shell 脚本
2. 缩小主 agent 的自动化范围，只保留轮次分发和状态汇总

### 风险 2：长会话失控

表现：子 agent 在单轮内扩散到过多文件或过多目标。

缓解：

1. 采用轮次制
2. 为单轮设置时长、步数和结果格式约束
3. diff 超阈值即终止该轮并回到主 agent 复盘

### 风险 3：共享文件提前冲突

表现：两个 worker 过早改同一共享文件。

缓解：

1. 禁改区默认收紧
2. 共享区改动统一由主 agent 或 foundation worker 收口
3. migration 一律视为共享风险

### 风险 4：测试补齐滞后

表现：功能推进快于测试，导致最终收口阶段集中暴雷。

缓解：

1. 把测试要求放进每轮交付条件
2. 不允许“功能先写完，测试最后补”成为默认策略

## 13. 验收标准

满足以下条件，视为本设计进入可实施状态：

1. Copilot CLI 可在主仓库和两个 worktree 中稳定启动会话。
2. 两个 worker 都已在编码前完成一次 fullstack-audit，且结果可被主 agent 消费。
3. 主 agent 可以独立启动并汇总两个 worker 的一轮执行结果。
3. 子 agent 的日志、状态、diff 和测试摘要可被主 agent 读取。
4. 高冲突区的禁改与冲突检测能够阻止双写。
5. 第一轮真实并行开发能在不改共享高冲突区的前提下完成两个最小闭环任务。

## 14. 结论

对于 x-claw，这套方案的核心不是“把 Copilot CLI 当作一个万能自治平台”，而是把它作为执行引擎，再由仓库内的 worktree、脚本、日志、状态文件和测试闸门把并行开发收束成一个可控系统。

因此，正式推荐路线为：

1. 先完成 CLI 能力校验。
2. 再由两个子 agent 先完成 fullstack-audit。
3. 然后实现最小编排骨架。
4. 再在两条功能线中以轮次制试运行。
5. 最后接入共享收口、pairwise 测试和最终合并流程。

本文件作为后续实现 Copilot CLI 多 agent 编排的唯一正式设计依据。
