## §2 与现有文档的冲突

### 2.1 冲突总览

| 现有文档 | 原假设 | 实际约束 | 冲突度 |
|---------|-------|---------|-------|
| [18 路线图](18-execution-roadmap.md) | 22 新 crate / 13 Wave / M0-M4 | 1 人 Rust 新手 · 8 月 | 🔴 **完全不可行** |

### 2.2 致命冲突详解

**冲突 #1: 工程量 vs 人力 (数量级错位)**

- 18 路线图 22 个新 crate,按场景 B (5 人 Rust 专家) 估算约 10-12 月到 MVP
- 现实 1 人 Rust 小白 · vibe coding · 8 个月
- **工作量倍率 ≈ 22-30 倍 gap** (5 人 × 1.2 倍 ÷ 1 人 × 0.2 倍新手效率)
- → **18 必须砍到原 1/5 以下**

**冲突 #2: 客户规模 vs 资源**

- Q8 答 D/E (1000-10000+ 人企业)
- 需要: 组织树 / 部门权限 / 配额 / SSO / 多租户隔离 / 审计不可篡改 / 高可用
- 这些**任何一项** 1 人做都要 1-2 月
- → **MVP 阶段无法服务这类客户**,必须接受"MVP 只做 POC 级别,生产级延到后续版本"

**冲突 #3: Q5 差异化 vs Q8 规模 vs Q10 合规**

- Q5 Top 3 全是安全 (DLP/凭证/沙箱) → 这是 **18 W0-W2 的核心**
- Q10 答 "先设计不做" → 但等保 3 级客户 (Q8 D/E 企业)会要求审计不可中断
- Q6 高端国央企 → 必须合规能过
- **矛盾**: 要卖高端安全,就不能"合规先设计不做"
- → 需要确认: MVP 先做 POC / 后续版本补合规,还是 POC 就带核心合规?

**冲突 #4: Windows 沙箱**

- 我上一轮猜"砍 dasclaw_sandbox_windows 9753 行"
- Q11 答客户端含 Windows 10/11 → **不能砍**
- → W7 沙箱层工作量维持原估,1 人不可能完成

## §3 三个 pivot 方向

### Pivot α: 极简 MVP (推荐 ⭐⭐⭐)

**思路**: 放弃"重做 22 个新 crate"Route B,回到"最小集成增强"Route。

**MVP 范围 (8 个月 1 人)**:
1. 保留现有 `ironclaw` / `claw-code/rust` / `admin-backend` 架构不动
2. **只新建 3 个 crate**:
   - `dasclaw_dlp_engine` (复用 Q5 #1 差异化) — 双向 DLP
   - `dasclaw_cred_boundary` (复用 Q5 #2) — 凭证 host 注入
   - `dasclaw_sandbox_kernel` (复用 Q5 #3) — 多层沙箱 facade (底下仍调 codex 的 landlock-sandbox / seatbelt-sandbox / spawn)
3. **Port 而非重写**: 直接把 codex-rs 相关 crate 作为依赖或 vendor,不做大规模 port
4. 国密: 软件算法 RustCrypto + sm3/sm4 crate 即可
5. Skills/Agent: 复用 claw-code 现有实现,补国产 LLM 适配
6. Admin-backend: 增强现有审计模块,不搞 Observer Chain 重构
7. 合规: 先设计文档 (符合 Q10 答案),不落地
8. 客户规模: MVP 只跑单租户 POC,多租户 / 组织树延到 v2

**放弃**:
- W3 Codex 对齐 (继续用原 codex 做后端即可)
- W4 Runtime 统一 (ironclaw/claw-code 各自保留)
- W5 Observer Chain (admin-backend 现有审计够用)
- W_Q3 可视化 Agent 编辑器 (延到 Y1 Q4)
- 组织树/部门权限 (延到 v2)

**Q15 达成度**: ✅ 2026 Q4 末可出 POC
**Q5 差异化兑现**: ✅ Top 3 能在 MVP 呈现 (POC 级)
**Q6 高端定位**: ⚠️ 需要承认 "v1 只服务标杆客户做 POC,v2 才生产"

### Pivot β: 外包/招聘补人

**思路**: 承认 1 人做不完,暂停 1-2 月招 2-3 个 Rust 中级工程师,走 21 场景 B。

**时间**:
- 招聘周期: 2-3 月
- 场景 B 交付: MVP 推到 2027 Q1-Q2
- 与 Q15 C (2026 Q4) **冲突**

**风险**: 新人上手 + 1 人 vibe coder 技术决策权矛盾

### Pivot γ: 放弃自研,基于开源组装

**思路**: 直接用 Dify / LangChain 做上层,只把"国产 LLM 适配 + DLP + 审计"三件事做成插件。

**冲击**: 15 §1 独特性归零,与 Q6 高端定位矛盾。不推荐,仅列出供对照。

## §4 推荐决策路径

### 4.1 建议选 Pivot α + 明确 MVP 定位为 "POC 级标杆客户验证"

**理由**:
- 唯一能在 1 人 · 8 月 · vibe coding 约束下达成 Q15 的路径
- 保住 Q5 Top 3 差异化的真实落地 (不是画饼)
- Q10 "合规先设计不做" 正好匹配 POC 阶段
- Q8 D/E 大客户留到 v2 是合理商业节奏 (标杆客户 → 生产级)

### 4.2 需要你进一步确认的 4 件事

1. **MVP 定位**: 是 "POC 级标杆验证" 还是 "1-2 个中小客户即可生产"?
2. **Route 选择**: Pivot α (极简自研) / β (招人) / γ (基于开源) / 其他?
3. **14 Claude Code 文档处理**: Q4 确认改名 "技术参考清单",是否同时**删除**14 中的"对标"章节?
4. **原 Route B 22 crate 规划**: 保留作为"未来愿景"(冻结到 v2/v3) 还是**彻底废弃**?
