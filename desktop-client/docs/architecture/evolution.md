# 架构演进历史

> 最后更新: 2025-01-XX

本文档记录 Desktop Client 架构的演进历史和重要决策。

## 时间线

```
2024-Q4: 初始版本 (HTTP + SSE)
   ↓
2025-01: 迁移到 Tauri IPC
   ↓
2025-01: 简化聊天架构
   ↓
未来: 完全独立
```

## 阶段 1: 初始版本 (HTTP + SSE)

### 架构

```
前端 (React)
  ├─ HTTP API → IronClaw Server (38080)
  └─ SSE → IronClaw Server (38080)
```

### 特点

- 前端直接调用 HTTP API
- 使用 EventSource 接收 SSE 事件
- 简单直接,快速实现

### 问题

1. **跨域问题**: 需要配置 CORS
2. **端口依赖**: 依赖固定端口 38080
3. **安全风险**: HTTP 端口暴露
4. **类型不安全**: 手动解析 JSON
5. **调试困难**: 需要网络工具

## 阶段 2: 迁移到 Tauri IPC (2025-01)

### 动机

- 解决跨域问题
- 提高安全性
- 统一通信机制
- 改善类型安全

### 架构变更

**之前**:
```
前端 → HTTP/SSE → IronClaw Server
```

**之后**:
```
前端 → Tauri IPC → Rust 后端 → IronClaw Server
```

### 实施步骤

1. **创建 Tauri 命令** (2025-01-10)
   - `send_chat_message`
   - `subscribe_chat_events`
   - `unsubscribe_chat_events`

2. **实现 SSE 订阅管理器** (2025-01-12)
   - 后台任务订阅 SSE
   - 解析事件并转发到前端
   - 管理订阅状态

3. **前端迁移** (2025-01-15)
   - 创建 `useAiChatTauri` Hook
   - 使用 Tauri 事件系统
   - 移除 HTTP API 调用

4. **测试和验证** (2025-01-18)
   - 单元测试
   - 集成测试
   - E2E 测试

### 成果

- ✅ 解决跨域问题
- ✅ 提高安全性
- ✅ 统一通信机制
- ✅ 改善类型安全
- ✅ 所有测试通过

### 遗留问题

- SSE 订阅管理复杂
- 容易出现内存泄漏
- 调试困难

## 阶段 3: 简化聊天架构 (2025-01)

### 动机

- SSE 订阅管理过于复杂
- 发现事件监听器泄漏问题
- 代码量过大 (~800 行)

### 架构变更

**之前**:
```
前端 → Tauri IPC → SSE 订阅管理器 → 后台任务 → SSE
```

**之后**:
```
前端 → Tauri IPC → 直接调用 API
```

### 实施步骤

1. **分析问题** (2025-01-20)
   - 识别内存泄漏
   - 评估复杂度
   - 提出简化方案

2. **评估方案** (2025-01-22)
   - 方案 1: 直接 HTTP (最简单)
   - 方案 2: 轮询 (实时性)
   - 方案 3: WebSocket (真正实时)

3. **决策** (2025-01-23)
   - 保留 Tauri IPC 架构
   - 简化 SSE 订阅逻辑
   - 改进事件监听器管理

4. **实施** (2025-01-25)
   - 修复事件监听器泄漏
   - 简化订阅管理
   - 优化错误处理

### 成果

- ✅ 修复内存泄漏
- ✅ 简化代码逻辑
- ✅ 改善可维护性
- ✅ 保持实时性

## 未来规划

### 阶段 5: 完全独立 (计划中)

**目标**: Desktop Client 完全独立,不依赖外部服务

**架构**:
```
前端 → Tauri IPC → Rust 后端 → IronClaw 核心库
```

**优点**:
- 单一进程
- 无端口依赖
- 更安全
- 更快速

**挑战**:
- 需要重构 IronClaw 核心为库
- 需要处理数据库访问
- 需要管理 Agent 生命周期

**时间线**: 3-6 个月

## 关键决策

### 决策 1: 选择 Tauri 而不是 Electron

**时间**: 2024-Q4

**理由**:
- 更小的体积 (~10MB vs ~100MB)
- 更好的性能 (Rust vs Node.js)
- 更高的安全性 (沙箱隔离)
- 原生体验 (系统 WebView)

**结果**: ✅ 正确决策,体验良好

### 决策 2: 迁移到 Tauri IPC

**时间**: 2025-01

**理由**:
- 解决跨域问题
- 提高安全性
- 统一通信机制

**结果**: ✅ 正确决策,问题解决

### 决策 3: 保留外部 IronClaw 服务

**时间**: 2025-01

**理由**:
- 职责分离
- 复用能力
- 灵活部署

**结果**: ✅ 正确决策,架构清晰

### 决策 4: 保留 rusqlite 依赖

**时间**: 2025-01

**理由**:
- 只读访问后端配置
- 简单直接
- 职责分离

**结果**: ✅ 正确决策,避免过度统一

## 经验教训

### 教训 1: 简单优于复杂

**问题**: SSE 订阅管理过于复杂

**教训**: 在满足需求的前提下,选择最简单的方案

**应用**: 简化聊天架构,减少 94% 代码

### 教训 2: 测试覆盖不等于质量

**问题**: 高测试覆盖率但仍有 bug

**教训**: 需要测试正常路径和错误路径

**应用**: 增加失败路径测试和安全审计测试

### 教训 3: 架构演进需要渐进

**问题**: 一次性大重构风险高

**教训**: 分阶段演进,每个阶段都可用

**应用**: 分 5 个阶段演进架构

### 教训 4: 文档和代码同步

**问题**: 文档过时,代码变更未同步

**教训**: 代码变更时同步更新文档

**应用**: 创建文档索引,定期审查
